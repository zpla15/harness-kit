# 작업 방식

> 작성일 2026-10-26 · v0.3
> harness-kit이 기획 앞뒤로 무엇을 하는지 정한다. 셋업, 구현 검수, 인계, 훅.
> 기획과 개발 스펙은 [설계](design.md)에 있다.

---

## 0. 한 장 요약

| 항목 | 내용 |
|---|---|
| 목표 | 기능 하나가 **셋업 → 기획 → 개발 스펙 → 코딩 → 검수 → 인계**로 끊기지 않고 이어지게 한다 |
| 하는 것 | 프로젝트 유형별 셋업, 문서 기준 구현 검수, 세션 사이 진행 기록 |
| 하지 않는 것 | 코딩 방식 강제(TDD, 계획 쪼개기 등), 개인 공통 규칙 만들기 |
| 남는 곳 | 프로젝트의 `.harness/` (설정, 진행 기록), `docs/product/{기능}/dev.md`의 작업 체크 |
| 사람의 일 | 유형과 커밋 방식 확인, 검수 결과 확인, 커밋·push·PR 승인 |

---

## 1. 전체 흐름

```text
/ks-setup   (프로젝트마다 한 번)  유형 판단 → 커밋 방식 → 검증 명령 → 기준선
   │
/ks-plan    기획 PRD, 기획 상세 스펙, 유저 플로우        (design.md)
/ks-dev     개발 스펙: 결정 … 작업(T) … 검증(V)         (dev-guide.md)
   │
 코딩        자유. 개발 스펙과 프로젝트 규칙을 보고 평소처럼 한다
   │
/ks-check   검증 명령 + 읽기 전용 검수 에이전트 ─ 부족하면 고치고 다시 ─▶ 모두 충족
   │
/ks-handoff 진행 기록 → 커밋·PR → 다음 할 일
```

| 상황 | 쓰는 명령 |
|---|---|
| 큰 기능, 정책이 애매함 | `/ks-plan` → `/ks-dev` → 코딩 → `/ks-check` → `/ks-handoff` |
| 기획이 이미 있음 | `/ks-dev` → 코딩 → `/ks-check` → `/ks-handoff` |
| 작은 수정, 버그 | 코딩 → `/ks-check` (가벼운 검수) → `/ks-handoff` |

코딩을 일부러 절차로 묶지 않는다. 뭘 만들지가 문서로 정해지면 코딩은 모델이 잘한다. 빠지기 쉬운 것은 **문서대로 됐는지 확인하는 일**과 **세션 사이에 이어가는 일**이라 그 둘만 단단히 한다.

## 2. 셋업 유형

| | 개인 | 팀 |
|---|---|---|
| 새 프로젝트 | 바로 만들고 main에 커밋 | 규칙 파일은 팀과 정하게 두고, 첫 PR로 올림 |
| 진행된 프로젝트 | 점검 → 빠진 것만 추가 → 커밋 | 점검 → 제안 → 브랜치 + PR. 남의 문서는 고치지 않음 |

- 판단 근거: 소스·커밋 수(새 프로젝트인지), 커밋 작성자 수와 원격 저장소 주인(팀인지).
- 판단은 추측이다. 근거와 함께 보여 주고 사람이 확인한다.
- 커밋 방식과 진행 기록을 git에 올릴지는 유형에 따라 추천하고 사람이 고른다.

## 3. `.harness/` 폴더

```text
<프로젝트>/.harness/
├─ config.json   유형, 커밋 방식, 검증 명령, 기준선
├─ progress.md   지금 상태, 다음 할 일, 막힌 것, 기록 (+ 훅의 자동 저장 칸)
├─ decisions.md  프로젝트 전체 결정 기록 (날짜, 결정, 이유, 버린 대안)
└─ history.md    progress.md에서 밀려난 오래된 기록
```

`config.json`:

| 키 | 값 |
|---|---|
| `type` | `새 개인` `진행된 개인` `새 팀` `진행된 팀` |
| `commit` | `main에 바로` `브랜치 + PR` |
| `track` | `true`면 `.harness/`를 git에 올린다. `false`면 `.git/info/exclude`로 뺀다 |
| `verify` | 검증 명령 목록. 앞에서부터 차례로 돌린다 |
| `decisions` | 결정 기록 경로. 기본 `.harness/decisions.md`, 프로젝트에 이미 있으면 그 경로 |
| `baseline` | 셋업 때 돌린 결과: `date` `passed` `failed` `knownFailures` |

팀 프로젝트는 `track: false`를 추천한다. 내 작업 기록이 팀 저장소에 섞이지 않고, 프로젝트 `.gitignore`도 건드리지 않는다.

## 4. 구현 검수

`/ks-check`는 개발 스펙을 기준으로 코드를 판정한다.

| 입력 | 어디서 |
|---|---|
| 작업(T), 검증(V) | `pp.mjs tasks <dev.md>` |
| T의 근거인 계약·오류·데이터 원문 | dev.md |
| 변경 범위 | `git diff` (브랜치 갈라진 곳 또는 마지막 인계 커밋부터) |
| 테스트 결과 | config의 `verify`, `baseline`과 비교 |

- **검수자는 따로 둔다.** 판정은 `ks-checker` 에이전트가 한다. 코드를 고칠 도구가 없고, 근거 `경로:줄`이나 테스트 이름을 대야 충족을 준다.
- 판정은 `충족` `부족` `확인 불가` 셋이다. 화면처럼 자동으로 볼 수 없는 것은 확인 방법을 적어 사람에게 넘긴다.
- **수렴할 때까지 돈다.** 부족 → 고침 → 다시 검수. 같은 항목이 세 번 연속 부족이면 멈추고 사람에게 넘긴다.
- 기준선의 `knownFailures`는 원래 실패하던 것이다. 새로 깨진 것만 내 책임으로 본다.
- 스펙에 없는 변경이 diff에 있으면 `기타`로 알린다.
- 충족한 작업만 `pp.mjs done`으로 dev.md에 `- [x]` 체크를 단다. 체크가 진행 상태의 기준이다.

개발 스펙이 없는 작은 일은 **가벼운 검수**다. 시킨 일 한 줄과 diff, 테스트 결과만 본다.

## 5. 인계와 훅

### 진행 기록

`/ks-handoff`가 `.harness/progress.md`를 정리한다.

| 칸 | 내용 |
|---|---|
| 지금 상태 | 하고 있는 일, 브랜치, 마지막 검수 |
| 다음 할 일 | 1~3개. 첫 줄은 바로 칠 수 있는 명령 |
| 막힌 것·정할 것 | 사람이 답할 것 |
| 기록 | 날짜, 한 일, 커밋·PR. 30줄이 넘으면 history.md로 |

### 결정 기록

| 어디에 | 무엇을 |
|---|---|
| 개발 스펙 `dev.md`의 D | 기능 하나 안의 결정 (그 기능 문서와 함께 산다) |
| `decisions.md` | 여러 기능이나 프로젝트 전체에 걸친 결정 (스택, 구조, 배포, 규칙) |

- `/ks-setup`이 셋업에서 정한 것을 첫 결정으로 쓰고, `/ks-handoff`가 세션에서 새로 정한 것을 더한다.
- 사람이 정한 것만 쓴다. 뒤집은 결정은 지우지 않고 `뒤집힘`으로 남긴다. 왜 바꿨는지가 다음 사람에게 필요하다.

### 훅

| 훅 | 언제 | 하는 일 |
|---|---|---|
| SessionStart | 새 세션, 이어하기, `/clear`, 압축 뒤 | config 요약, progress.md, 최근 결정 5개 제목, 남은 작업(T), 진행 중인 기획 폴더를 대화 맥락에 넣는다 |
| PreCompact | 대화가 압축되기 직전 | progress.md 맨 아래 `## 자동 저장` 칸에 시각, 브랜치, 최근 커밋, 바뀐 파일, 남은 작업을 덮어쓴다 |

- 훅은 `.harness/`도 기획 폴더도 없는 프로젝트에서는 아무것도 하지 않는다.
- 훅은 실패해도 세션을 막지 않는다. 항상 종료 코드 0으로 끝난다.
- 자동 저장은 위쪽 칸을 건드리지 않는다. 다음 `/ks-handoff`가 읽어서 위쪽에 반영하고 지운다.

## 6. 규칙과의 관계

- 개인 공통 규칙(모든 프로젝트에 같이 쓰는 내 규칙)은 이 플러그인 밖, 사용자 전역 CLAUDE.md에 둔다. 플러그인은 읽고 지키기만 한다.
- 프로젝트 규칙(CLAUDE.md, AGENTS.md, 컨벤션 문서)이 공통 규칙과 부딪히면 프로젝트 규칙을 따른다.
- 개발 스펙의 5-10 규칙 대조와 `/ks-check`는 같은 규칙 파일을 본다.

## 7. 하네스 명령

| 명령 | 하는 일 |
|---|---|
| `node scripts/pp.mjs tasks <dev.md 또는 폴더>` | 작업(T)과 검증(V)을 JSON으로 낸다. 남은 작업이 있으면 종료 코드 1 |
| `node scripts/pp.mjs done <dev.md 또는 폴더> <T번호...>` | 그 작업 줄의 `- [ ]`만 `- [x]`로 바꾼다 |
| `node scripts/hook.mjs session-start` | 훅용. 표준 입력의 `cwd` 프로젝트 진행 기록을 출력한다 |
| `node scripts/hook.mjs pre-compact` | 훅용. 자동 저장 칸을 쓴다 |

내보낸 `docs/product/{기능}/dev.md`(링크가 붙은 모양)와 작업 폴더의 dev.md를 둘 다 읽는다.
