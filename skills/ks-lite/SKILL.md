# 가볍게 같이 정하기

요청: $ARGUMENTS

작업 방식은 이 스킬 폴더 기준 `../../docs/workflow.md` 1장. 하네스는 `node <플러그인 루트>/scripts/pp.mjs` (플러그인 루트 = 이 스킬 폴더의 두 단계 위).

## 1. 지켜야 할 것

- **바로 코딩하지 않는다.** 정할 것이 남아 있는 동안은 묻고, 사용자가 "됐어", "ㄱㄱ", "만들어"라고 하면 그때 정리하고 만든다.
- **묻기 전에 먼저 코드를 읽는다.** 코드로 알 수 있는 것(지금 구조, 쓰는 라이브러리, 비슷한 기존 기능)은 묻지 않는다. 질문에는 읽은 근거 `경로:줄`을 붙인다.
- **빈 질문 말고 문제와 선택지로 묻는다.** "어떻게 할까요?"가 아니라 "이렇게 하면 이런 문제가 있어요. A / B 중 어떻게 할까요?"로 묻는다.
- 한 번에 질문 **1~3개**, `AskUserQuestion`으로. 선택지 2~4개, 추천은 첫 선택지에 `(추천)`과 이유 한 줄.
- 답을 받으면 **그 답 때문에 새로 생기는 문제**를 다시 찾는다. 답 하나로 끝내지 않는다.
- 사용자가 "알아서 해", "추천대로"라고 하면 추천안으로 정하고 정한 것에 `(추천대로)`라고 남긴다.
- 사소한 것(변수 이름, 파일 위치처럼 기존 패턴을 따르면 되는 것)은 묻지 않고 기존 패턴을 따른다.

## 2. 시작

1. 요청이 비어 있으면 무엇을 하고 싶은지 한 줄로 묻는다.
2. 관련 코드, `docs/product/`, `.harness/decisions.md`, 프로젝트 규칙 파일을 읽는다.
3. 이해한 것을 2~3줄로 다시 말한다: "이렇게 이해했어요: …". 틀렸으면 고친다.
4. 3장의 렌즈로 문제를 찾아 첫 질문을 한다.

## 3. 찾아서 짚을 것 (렌즈)

질문거리는 아래에서 찾는다. 이 기능에 해당하는 것만 골라 중요한 것부터 묻는다.

| 렌즈 | 예 |
|---|---|
| 범위 | 이것도 같이 하나요? 이번엔 빼나요? |
| 누가 | 권한, 로그인 안 한 사용자, 관리자 |
| 경계·실패 | 빈 값, 중복, 동시에 두 번, 네트워크 실패, 시간대 |
| 기존 것과 부딪힘 | 이미 있는 기능·API·데이터와 겹치거나 바뀌는 곳 |
| 데이터 | 저장 모양, 기존 데이터 이전, 지우면 어떻게 되나 |
| 보안·개인정보 | 남의 것을 볼 수 있나, 입력 검증, 비밀값 |
| 성능·비용 | 많아지면, 자주 부르면, 외부 API 요금 |
| 사용자 경험 | 기다리는 동안, 실패했을 때 무엇이 보이나 |
| 확인 방법 | 다 됐다는 걸 무엇으로 확인하나 |

## 4. 매 턴의 모양

```text
정리  ✅ 예약 취소 가능 · ✅ 최대 30일 뒤까지 · ❓ 발송 실패 시 · ❓ 시간대
───
발송 시각에 메일 서버가 응답하지 않으면 편지가 사라질 수 있어요.
근거 코드  src/letters/send.ts:22 (지금은 실패하면 로그만 남김)
```

그 아래에 `AskUserQuestion`으로 질문 1~3개. 정리 줄은 매 턴 맨 위에 짧게 다시 보여 준다. 정한 것은 ✅, 남은 것은 ❓.

## 5. 언제 끝내나

- ❓가 없고 렌즈에서 더 찾을 것이 없으면 "더 정할 건 없어 보여요. 정리할까요?"라고 묻는다.
- 사용자가 끝내자고 하면 ❓가 남아 있어도 끝낸다. 남은 것은 정리의 `남은 문제`에 쓰고, 그 부분은 추천안으로 만들지 묻는다.
- 정할 것이 **10개를 넘거나** 여러 사람이 볼 기능이면 `/ks-plan`으로 갈지 묻는다. 가면 지금까지 정한 것을 첫 답으로 넘긴다.

## 6. 정리 남기기

`.harness/lite/{기능 영어 이름}.md`에 쓴다. `.harness/`가 없으면 만들기 전에 `/ks-setup`을 할지 묻고, 안 하면 이 파일만 만든다.

```md
# 편지 예약 발송

상태: 확정
날짜: 2026-10-26

## 목표

예약한 시각에 편지가 간다.

## 정한 것

- 예약 취소 가능. 이유: 사용자가 마음을 바꿀 수 있다.
- 최대 30일 뒤까지 (추천대로)

## 남은 문제

## 요구사항

- R1 편지를 원하는 시각에 보낸다
  - R1-1 예약 시각이 되면 1분 안에 발송된다
  - R1-2 과거 시각 예약은 거절한다

## 작업 계획

- [ ] T1 편지에 예약 시각을 둔다. 근거: R1
- [ ] T2 예약·취소 API를 만든다. 근거: R1-2

## 검증

- V1 R1-1 · 1분 뒤로 예약하면 1분 안에 발송된다.
- V2 R1-2 · 어제 시각으로 예약하면 거절된다.
```

- 작업과 검증 줄 모양은 정확히 위와 같아야 `/ks-check`가 읽는다. 쓴 뒤 `pp.mjs tasks <파일>`로 읽히는지 확인한다.
- 요구사항마다 완성 기준을 1개 이상, 완성 기준마다 검증 V를 1개 이상 둔다.
- 프로젝트 전체에 걸친 결정(라이브러리 도입, 구조 변경)이 있었으면 `.harness/decisions.md`에도 남길지 묻는다.
- 정리를 보여 주고 확인받는다.

## 7. 다음

- "바로 만들까요?"라고 묻는다. 만들면 작업 T 순서대로 코딩한다.
- 코딩이 끝나면 `/ks-check .harness/lite/{기능}.md`로 검수한다. 검수 전에 다 됐다고 하지 않는다.
- 멈출 때는 `/ks-handoff`.
