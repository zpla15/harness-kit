# 가볍게 묻고 결론 내기

요청: $ARGUMENTS

문서를 쓰지 않는다. 대화로 빈 곳을 채우고 **결론**을 내는 것이 목적이다.

## 1. 지켜야 할 것

- **바로 만들지 않는다.** 먼저 묻고, 결론을 확인받은 뒤에 만든다.
- **묻기 전에 코드를 읽는다.** 코드로 알 수 있는 것은 묻지 않는다. 질문에 읽은 근거 `경로:줄`을 붙인다.
- **문제와 선택지로 묻는다.** "어떻게 할까요?"가 아니라 "이러면 이런 문제가 있어요. A / B 중 어떻게 할까요?"
- 한 번에 1~3개, `AskUserQuestion`으로. 선택지 2~4개, 추천은 첫 선택지에 `(추천)`과 이유 한 줄.
- **결론에 영향이 있는 것만 묻는다.** 기존 패턴을 따르면 되는 것, 나중에 바꿔도 되는 것은 묻지 않고 정해서 결론에 적는다.
- 답을 받으면 그 답 때문에 새로 생긴 문제가 있는지 한 번 더 본다.
- "알아서 해", "추천대로"면 추천안으로 정한다.
- 파일을 만들지 않는다. 사용자가 저장하자고 하면 그때 `.harness/progress.md`나 원하는 곳에 남긴다.

## 2. 흐름

1. 관련 코드와 프로젝트 규칙, `.harness/decisions.md`를 읽는다.
2. 이해한 것을 1~2줄로 말한다: "이렇게 이해했어요: …"
3. 빈 곳을 찾아 역질문한다 (3장 렌즈).
4. 답마다 짧은 정리 줄을 맨 위에 다시 보여 준다: `✅ 정한 것 · ❓ 남은 것`
5. ❓가 없으면 결론을 낸다 (4장). 사용자가 중간에 "됐어"라고 하면 남은 것은 추천안으로 채워 결론을 낸다.

보통 2~4번 주고받으면 끝난다. 정할 것이 10개를 넘거나 여러 사람이 볼 기능이면 `/ks-plan`을 권한다.

## 3. 빈 곳을 찾는 렌즈

이 요청에 해당하는 것만, 중요한 것부터.

| 렌즈 | 예 |
|---|---|
| 범위 | 이것도 같이 하나요? 이번엔 빼나요? |
| 누가 | 권한, 로그인 안 한 사용자, 관리자 |
| 경계·실패 | 빈 값, 중복, 동시에 두 번, 네트워크 실패, 시간대 |
| 기존 것과 부딪힘 | 이미 있는 기능·API·데이터가 바뀌거나 겹치는 곳 |
| 데이터 | 저장 모양, 기존 데이터, 지우면 어떻게 되나 |
| 보안 | 남의 것을 볼 수 있나, 입력 검증, 비밀값 |
| 성능·비용 | 많아지면, 자주 부르면, 외부 API 요금 |
| 사용자 경험 | 기다리는 동안, 실패했을 때 무엇이 보이나 |

## 4. 결론

```text
결론  편지 예약 발송

할 일
1. letters에 scheduled_at 컬럼 추가 (기존 편지는 null = 즉시 발송)
2. POST /letters/:id/schedule, DELETE로 취소
3. 1분마다 도는 발송 작업. 서버가 꺼져 있다 켜지면 밀린 것부터 보냄

정한 것   취소 가능 · 최대 30일 · 과거 시각 거절 · 실패하면 3번 재시도 (추천대로)
안 하는 것  예약 수정 (취소 후 다시 예약)
확인 방법  1분 뒤 예약 → 1분 안에 발송 / 어제 시각 → 거절
```

- 할 일은 순서대로 3~7줄. 파일·API 이름처럼 바로 손댈 수 있는 수준으로 쓴다.
- 확인 방법은 `/ks-check`의 가벼운 검수가 그대로 쓸 수 있게 "이렇게 하면 이렇게 된다" 모양으로 쓴다.
- 프로젝트 전체에 걸친 결정(라이브러리 도입, 구조 변경)이 있었으면 `.harness/decisions.md`에 남길지 묻는다.
- 마지막에 "이대로 만들까요?"라고 묻는다. 만들면 할 일 순서대로 코딩하고, 끝나면 `/ks-check`로 확인 방법을 검수한다.
