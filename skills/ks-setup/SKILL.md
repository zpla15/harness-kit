# 셋업

프로젝트: $ARGUMENTS (비어 있으면 지금 대화를 연 프로젝트)

작업 방식 전체는 이 스킬 폴더 기준 `../../docs/workflow.md`에 있다. 시작할 때 한 번 읽는다.

## 1. 지켜야 할 것

- 처음 두 단계(살펴보기, 점검 보고)는 **읽기만** 한다. 파일은 사용자가 확인한 뒤에 만든다.
- 이미 있는 파일(CLAUDE.md, AGENTS.md, README, 설정 파일)은 덮어쓰지 않는다. 고칠 곳이 보이면 보여 주고 묻는다.
- 팀 프로젝트에서 남이 쓴 문서와 설정은 묻지 않고 고치지 않는다.
- 스택, 배포처럼 사람이 정할 것은 추측해서 채우지 않는다. 후보 2~3개를 장단점과 함께 보여 주고 고르게 하고, 고른 결과는 결정 기록에 남긴다.
- 질문은 `AskUserQuestion`으로 한 번에 1~3개, 추천은 첫 선택지에 `(추천)`과 이유 한 줄.
- 공통 규칙(사용자 개인 규칙)은 이 플러그인이 만들지 않는다. 사용자 전역 CLAUDE.md와 프로젝트 규칙 파일을 읽고 지키기만 한다.

## 2. 살펴보기 (읽기만)

1. `.harness/config.json`이 이미 있으면 내용을 보여 주고, 바꿀 것이 있는지 묻는다. 없으면 여기서 끝낸다.
2. 다음을 읽는다.
   - 루트 파일, README, `docs/`, 패키지·빌드 파일, CLAUDE.md·AGENTS.md·CLAUDE.local.md, 테스트 설정
   - `git log --oneline -20`, `git shortlog -sne --all | head`, `git remote -v`, 지금 브랜치
   - `docs/product/` 아래 기능 문서, `.product-planning/` 아래 진행 중인 기획

## 3. 유형 판단

| 질문 | 판단 근거 |
|---|---|
| 새 프로젝트인가 | 소스 파일이 거의 없고 커밋이 몇 개 안 되면 새 프로젝트 |
| 팀 프로젝트인가 | 커밋 작성자가 2명 이상이거나, 원격 저장소 주인이 조직(organization)이면 팀 |

판단을 근거와 함께 보여 주고 확인받는다. 예: "진행된 팀 프로젝트로 보여요 (원격 vibe-million/…, 작성자 3명). 맞나요?"
유형은 `새 개인` `진행된 개인` `새 팀` `진행된 팀` 가운데 하나다.

## 4. 점검 보고

진행된 프로젝트면 아래 표로 보고한다. 새 프로젝트면 "없음"이 대부분이니 표 없이 만들 것만 말한다.

| 부분 | 있는 것 | 빠진 것 | 서로 다른 말을 하는 곳 |
|---|---|---|---|
| 지시 | 규칙 파일, 문서 지도 | | |
| 검증 | 테스트·빌드·린트 명령 | | |
| 상태 | 진행 기록, 결정 기록 | | |
| 기획 | `docs/product/` 기능 문서 | | |

문서끼리 다른 말을 하면(예: README의 테스트 명령과 package.json이 다름) 어느 쪽이 맞는지 묻는다.

## 5. 정하기

한 번에 묻는다.

1. **커밋 방식** — 유형에 따라 추천한다.

   | 유형 | 추천 |
   |---|---|
   | 새 개인, 진행된 개인 | main에 바로 |
   | 새 팀, 진행된 팀 | 브랜치 + PR |

2. **진행 기록을 git에 올릴지** — 개인은 올림(추천), 팀은 내 PC에만 둠(추천). 팀원에게 내 작업 기록을 보이지 않게 하려는 것이다.
3. **검증 명령** — 찾은 명령(예: `npm test`, `npm run lint`)을 보여 주고 확인받는다. 없으면 스택에 맞는 후보를 제안한다.

## 6. 만들기

확인받은 뒤 만든다. 만들기 전에 파일 목록을 먼저 말한다.

1. `.harness/config.json` — [templates/config.json](templates/config.json) 모양으로 채운다.
2. `.harness/progress.md` — [templates/progress.md](templates/progress.md)를 채운다. 다음 할 일 칸에 첫 할 일을 적는다.
3. `.harness/decisions.md` — [templates/decisions.md](templates/decisions.md)의 머리말만 쓰고 예시 결정은 뺀다. 셋업에서 정한 것(스택, 커밋 방식, 검증 명령 등)을 첫 결정들로 남긴다.
   - 프로젝트에 이미 결정 기록(`DECISIONS.md`, `docs/adr/` 등)이 있으면 새로 만들지 않고 그 경로를 config의 `decisions`에 적는다.
4. 진행 기록을 git에 올리지 않기로 했으면 `.git/info/exclude`에 `.harness/` 한 줄을 더한다. 프로젝트 `.gitignore`는 건드리지 않는다.
5. 규칙 파일이 없을 때만:
   - 개인: `CLAUDE.md`를 50줄 안쪽으로 만든다. 프로젝트 목적 한 줄, 폴더 지도, 검증 명령, 하지 말 것만 쓴다.
   - 팀: 만들지 않고 "규칙 파일이 없어 팀과 정해 추가하길 권한다"고만 알린다.
6. 새 프로젝트이고 테스트가 하나도 없으면, 통과하는 예제 테스트 1개와 테스트 명령을 만들지 묻는다.

## 7. 기준선

1. 검증 명령을 **직접** 돌린다.
2. 결과를 `config.json`의 `baseline`에 남긴다: 날짜, 통과 수, 실패 수, 원래 실패하던 테스트 이름.
3. 원래 실패하던 것이 있으면 사용자에게 보여 준다. 고치지 않는다. `/ks-check`가 이것과 비교해 "내가 깨뜨린 것"만 골라낸다.
4. 명령이 아예 안 돌면(설치 안 됨 등) 원인과 고칠 방법을 알리고, 기준선은 `null`로 둔다.

## 8. 끝

- 만든 파일과 정한 것을 표로 보여 준다.
- 커밋 방식대로 커밋할지 묻는다. 브랜치 + PR이면 브랜치를 만들고, push와 PR 생성은 다시 묻는다.
- 다음 흐름을 한 줄로 알린다: `새 기능은 /ks-plan → /ks-dev → 코딩 → /ks-check → /ks-handoff`
